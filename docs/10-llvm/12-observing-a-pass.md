# 12 — 观察一个后端 pass：四件工具

调后端 pass 的主力**不是 gdb**。下面四件按使用频率排，前三件覆盖 90% 的场景。

## 1. 看 pass 前后的 MIR

```bash
llc -mtriple=riscv32 -O2 -print-after-all t.ll -o /dev/null 2> dump.txt
```

- `-print-after-all` — 每个 pass 跑完都把整个函数的 MIR 打一遍。输出**非常长**（一个两行的 C 函数就有 113 个 pass 边界），所以一定重定向。
- 输出走 **stderr**，所以是 `2>` 不是 `>`。

只关心某一个 pass 时用精确版，输出小几个数量级：

```bash
llc -mtriple=riscv32 -O2 \
    -print-before=riscv-load-store-opt -print-after=riscv-load-store-opt \
    t.ll -o /dev/null
```

`-print-before=` / `-print-after=` 的参数是 pass 的**命令行名**（不是类名）。命令行名从哪来见 §4。

## 2. 看 pass 内部说了什么：`-debug-only`

LLVM 里每个 `.cpp` 顶部会定义：

```cpp
#define DEBUG_TYPE "riscv-load-store-opt"
```

然后代码里用 `LLVM_DEBUG(dbgs() << "...")` 写调试输出。`-debug-only=<DEBUG_TYPE>` 只打开指定文件的这些输出：

```bash
llc -mtriple=riscv32 -O2 -debug-only=riscv-load-store-opt t.ll -o /dev/null
```

### ⚠ 这需要一个开了 assertions 的构建

`LLVM_DEBUG` 和整个 `-debug` / `-debug-only` 机制都包在 `#ifndef NDEBUG` 里面。`CMAKE_BUILD_TYPE=Release` 会定义 `NDEBUG`，于是这些代码**被整体编掉**，选项本身都不存在：

```
llc: Unknown command line argument '-debug-only=riscv-load-store-opt'.
```

解法是构建时加 `-DLLVM_ENABLE_ASSERTIONS=ON`。它的作用是**去掉 `NDEBUG` 但保留 `-O3`** ——不是切到 Debug 构建。代价是 clang/llc 慢一些、二进制大一些；收益是 `LLVM_DEBUG` 全部回来，外加 `assert()` 能抓住大量 pass 逻辑错误。

**对 pass 开发来说这不是可选项**。建议留两套构建：出货用的 Release（不带 assertions），和一套带 assertions 的用来做实验。

## 3. 单独跑一个 pass：`-stop-after` / `-run-pass`

这是后端 pass 开发的**核心工作流**，也是写测试的基础。两步：

```bash
# 第一步：跑到某个 pass 之后停下，把 MIR 存成文本
llc -mtriple=riscv32 -O2 -stop-after=prologepilog t.ll -o t.mir

# 第二步：只跑你关心的那一个 pass，输入是上面那份 MIR
llc -mtriple=riscv32 -mattr=+Xmipslsp -use-riscv-mips-load-store-pairs=1 \
    -run-pass=riscv-load-store-opt t.mir -o -
```

- `-stop-after=<pass>` — 跑到该 pass **之后**停止，输出 MIR 文本而不是汇编。（对应的 `-stop-before=` 是之前停。）
- `-run-pass=<pass>` — **只**跑这一个（或逗号分隔的几个）pass，输入必须是 MIR。
- `-o -` — 输出到 stdout。

为什么这套比 gdb 有用：输入是一份**文本**，你可以手改 MIR 构造任意边界情况，然后只跑目标 pass，直接看输出。迭代一次是秒级，而且这份 `.mir` 直接就能变成一个测试用例。

## 4. pass 的命令行名从哪来

从注册宏。`INITIALIZE_PASS` 的第二个参数就是命令行名，通常直接写成 `DEBUG_TYPE`：

```cpp
#define DEBUG_TYPE "riscv-load-store-opt"
#define RISCV_LOAD_STORE_OPT_NAME "RISC-V Load / Store Optimizer"
...
INITIALIZE_PASS(RISCVLoadStoreOpt, DEBUG_TYPE, RISCV_LOAD_STORE_OPT_NAME, false, false)
```

所以**同一个字符串同时是** `-debug-only=` 的参数、`-run-pass=` 的参数、`-print-after=` 的参数。类名（`RISCVLoadStoreOpt`）不是。

注册一个后端 pass 需要四个动作，缺一不可：

1. `RISCV.h` 里声明 `FunctionPass *createXxxPass();` 和 `void initializeXxxPass(PassRegistry &);`
2. `.cpp` 里用 `INITIALIZE_PASS` 宏定义（它展开成 pass 的静态注册代码与 `ID`）
3. `LLVMInitializeRISCVTarget()`（在 `RISCVTargetMachine.cpp`）里调 `initializeXxxPass(*PR)`
4. `llvm/lib/Target/RISCV/CMakeLists.txt` 的 `add_llvm_target(RISCVCodeGen ...)` 源文件列表里加上这个 `.cpp`

漏掉第 4 步文件根本不参与编译；漏掉第 3 步 `-run-pass=` 会说找不到这个 pass。

## 5. 测试：lit + FileCheck

LLVM 的回归测试是"跑一条命令，用注释里的模式去匹配它的输出"。

```
; RUN: llc -mtriple=riscv32 -mattr=+xqcilsm -run-pass=riscv-load-store-opt %s -o - | FileCheck %s
```

- `RUN:` 行由 **lit**（测试驱动器）执行，`%s` 替换成测试文件自己的路径。
- 输出管给 **FileCheck**，它读同一个文件里的 `CHECK:` / `CHECK-NEXT:` / `CHECK-NOT:` 等指令去匹配。
- MIR 测试的 `CHECK` 行通常由 `llvm/utils/update_mir_test_checks.py` 自动生成（`.ll` 测试对应 `update_llc_test_checks.py`），文件头会有一行 `NOTE: Assertions have been autogenerated by ...` 说明——**这种文件不要手改 CHECK 行，重新跑一遍脚本**。

跑单个测试目录：

```bash
ninja -C <build 目录> check-llvm-codegen-riscv
```

lit 与 FileCheck 由 ninja 按需构建，不需要单独装。
